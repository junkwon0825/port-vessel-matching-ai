# Port Vessel Matching AI · Portfolio Case Study

## 프로젝트 요약

항만 입출항 신고 기록과 표준 선박 카탈로그 사이의 표기 차이를 해소하는 엔터티 매칭 시스템을 구현했습니다. 입력 기록마다 78,595척 중 하나의 `vessel_id`를 선택합니다.

- 프로젝트 형태: 3인 팀 대회 참가
- 문제 유형: Entity Resolution / Record Linkage / Learning-to-Rank
- 개발 언어: Python 3.11
- 핵심 기술: TF-IDF, RapidFuzz, LightGBM LambdaRank
- 평가식: `0.7 × 한글 정확도 + 0.3 × 비한글 정확도`

## 해결하려던 문제

실제 항만 기록은 선박명이 표준 카탈로그와 정확히 일치하지 않습니다. 한글과 영문 표기가 섞이고 띄어쓰기, 철자, 약칭이 달라집니다. 선박명이 같아도 서로 다른 선박일 수 있으며, 톤수에는 오차와 결측이 존재합니다.

완전 일치 검색만 사용하면 반복해서 관측된 선박은 맞출 수 있지만 처음 보는 선박에는 대응하기 어렵습니다. 반대로 모든 카탈로그 행과 복잡한 유사도를 계산하면 평가 서버의 시간과 메모리 제약을 넘을 수 있습니다.

## 핵심 판단 1 · 선박 단위 검증

처음에는 행을 무작위로 분할하면 동일 선박의 기록이 학습과 검증 양쪽에 들어갈 수 있다는 문제를 확인했습니다. 호출부호와 정규화 이름을 직접 조회하는 방식은 반복 선박 검증에서 1.0 정확도를 보였지만, 선박 ID가 겹치지 않는 검증에서는 정답을 찾지 못했습니다.

따라서 `target_vessel_id`를 기준으로 학습과 검증을 분리했습니다.

- 학습 행: 9,752
- 검증 행: 2,470
- 학습·검증 선박 ID 중복: 0
- 검증 선박 ID: 1,170

이 분할은 리더보드 점수를 모사하기 위한 완벽한 방법은 아니지만, 단순 암기 효과를 제거하고 미관측 선박 검색 능력을 비교하는 데 적합했습니다.

## 핵심 판단 2 · 검색과 랭킹 분리

전체 카탈로그를 정밀 비교하는 대신 두 단계로 나눴습니다.

1. 빠른 후보 검색이 정답 가능성이 있는 최대 600척을 모읍니다.
2. 정밀 특징과 LightGBM Ranker가 후보 순위를 다시 계산합니다.

후보 검색은 문자 단위 TF-IDF, 메타데이터 조합, 톤수 근접 검색을 합칩니다. 이 단계에서 전체 Recall@600 0.9951을 확보해 랭커가 정답을 선택할 수 있는 기반을 만들었습니다.

## 핵심 판단 3 · Hard Negative 학습

무작위 오답은 정답과 너무 달라 쉽게 구분됩니다. 실제 추론에서 문제가 되는 후보는 이름이나 톤수가 비슷해 검색 상위에 올라온 선박입니다.

각 학습 기록마다 검색 상위 오답 40개를 Hard Negative로 선택했습니다. 전체 공개 학습 데이터로 최종 학습할 때 12,222개 query group과 501,102개 pair를 구성했습니다.

## 핵심 판단 4 · 언어별 전략

실험 결과 비한글 기록에서는 검색 1순위가 강했고, 한글 기록에서는 언어 가중치를 적용한 Ranker가 더 높은 정확도를 보였습니다.

| 전략 | 한글 | 비한글 | 가중 점수 |
|---|---:|---:|---:|
| 검색 1순위 | 0.1901 | 0.9206 | 0.4092 |
| 가중 Ranker | 0.5785 | 0.8016 | 0.6454 |
| 언어별 Hybrid | 0.5785 | 0.9206 | 0.6811 |

한글은 Ranker, 비한글은 검색 순위를 선택한 Hybrid가 두 방식의 장점을 유지했습니다.

## 모델 특징

40개 pair feature는 다음 범주로 구성했습니다.

- 검색 순위와 역순위
- 원문과 로마자 선박명 문자열 유사도
- bigram·trigram Jaccard와 접두어 유사도
- 총톤수·국제총톤수의 상대 오차
- 국적·선종 일치 여부
- 메타데이터 조합의 빈도와 확률
- 카탈로그 제원 비율

LightGBM의 `lambdarank` objective를 사용해 각 기록 안에서 정답 후보가 높은 순위에 오르도록 학습했습니다.

## 평가 서버 대응

대회는 모델 파일과 추론 코드를 ZIP으로 제출하고, 인터넷이 차단된 평가 서버에서 실행하는 방식이었습니다.

- `script.py`가 서버의 `data/test.csv`와 `data/vessel_catalog.csv`를 읽음
- 학습 과정 없이 저장된 Ranker를 로드해 추론
- 행 수와 `sample_id`를 코드에 고정하지 않음
- `output/submission.csv`를 지정된 형식으로 생성
- NumPy, pandas, scikit-learn은 서버 기본 패키지를 사용해 설치 충돌을 줄임

## 배운 점

엔터티 매칭에서는 최종 분류기보다 검증 분할과 후보 검색이 먼저입니다. 정답이 후보에 없으면 복잡한 Ranker도 복구하지 못합니다. 또한 전체 평균 정확도만 보면 비한글 다수 데이터에 가려 한글 성능 문제가 작게 보일 수 있습니다. 평가식과 운영 대상을 기준으로 그룹별 지표를 함께 봐야 합니다.

## 후속 개선

- 한글 선박명 음역과 로마자 변형 사전 학습
- 후보 검색 모델의 학습형 임베딩 적용
- Ranker 확률 보정과 Top-k 추천 신뢰도 제공
- 정비 담당자가 이름·톤수·국적 근거를 확인할 수 있는 설명 화면
- 신규 기록을 검수 결과와 함께 재학습하는 Human-in-the-loop 구조
